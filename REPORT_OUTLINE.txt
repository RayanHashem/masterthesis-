CHAPTER 1: INTRODUCTION & PROBLEM STATEMENT
================================================================================

- Lebanon faces significant challenges in Emergency Medical Services (EMS)
  coverage due to uneven geographic distribution of stations, varying population
  densities, and complex terrain.
- There is no publicly available spatial planning tool that helps decision-makers
  identify where new EMS stations should be placed.
- This project develops a multi-criteria decision support system using the
  Analytic Hierarchy Process (AHP) to evaluate and prioritize Lebanon's 26
  districts (qadaa level) for new EMS station placement.
- The system produces an interactive web-based dashboard with live AHP model
  controls, an integrated AI chat assistant (EMS Copilot), and data-driven
  candidate station recommendations.
- All processing runs locally on the user's machine; no data leaves the device.

CHAPTER 2: LITERATURE REVIEW & THEORETICAL BACKGROUND
================================================================================

2.1 Emergency Medical Services (EMS) Response Standards
- Lebanese Red Cross / IFRC International Network Plan 2023 [LRC-9]:
  Target = respond to 80% of emergency calls within 9 minutes.
- Lebanese Red Cross / IFRC INP 2023 [LRC-13]:
  Secondary target = respond to 85% of calls within 13 minutes.
- European standard [EU-8]: 8 minutes for life-threatening (critical) calls.
- WHO Clinical Services & Systems framework: defines ambulance base station as
  a facility equipped for personnel and restocking.
- Lebanese Ministry of Public Health, Karar (Decision) No. 473/2021 [MoPH-473]:
  Licenses EMS/ambulance operators. Spatial spacing is NOT publicly codified.

2.2 Analytic Hierarchy Process (AHP)
- AHP is a structured multi-criteria decision-making (MCDM) method developed
  by Thomas L. Saaty (1980).
- Decomposes complex decisions into a hierarchy of criteria.
- Allows assigning weights to criteria based on relative importance.
- Produces a single composite score per alternative for ranking.
- Widely used in facility location problems, healthcare planning, and
  resource allocation.

2.3 GIS in Healthcare Planning
- Geographic Information Systems (GIS) enable spatial analysis of healthcare
  accessibility.
- Network analysis (road graphs) provides realistic travel time estimates
  compared to straight-line (Euclidean) distance.
- Combination of AHP + GIS is well-established in the literature for optimal
  facility siting.

2.4 Key Distinction: No ArcGIS Used
- This project uses an entirely open-source geospatial stack.
- No ESRI products (ArcGIS, ArcMap, ArcPro) are used.
- All spatial analysis is performed with Python libraries (GeoPandas, OSMnx,
  Shapely, Rasterio, Folium).

CHAPTER 4: DATA SOURCES & COLLECTION
================================================================================

4.1 District Boundaries
- Source: GADM version 4.1 (Global Administrative Areas Database)
- URL: https://gadm.org
- File: gadm41_LBN_2.json (GeoJSON format)
- Contains: 26 district polygons (MultiPolygon geometry) with NAME_2 (district
  name) and NAME_1 (governorate name)
- Coordinate system: WGS84 (EPSG:4326)
- Note: Some districts appear as duplicate entries in GADM (e.g., two "Batroun"
  polygons). The pipeline dissolves these by NAME_2, summing population and
  station counts.

4.2 EMS Station Locations
- Source: Operational dataset (EMS_Station_Locations.xlsx)
- Format: Excel spreadsheet with latitude/longitude columns
- Total stations: 52
- Columns used: latitude (Y), longitude (X), station identifiers
- Spatial join assigns each station to its containing district

4.3 Population Data
- Source: WorldPop 2025 Constrained (CN) dataset
- URL: https://www.worldpop.org
- File: lbn_pop_2025_CN_1km_R2025A_UA_v1.tif (GeoTIFF raster)
- Resolution: 1 km x 1 km grid cells
- Values: estimated persons per pixel
- Coordinate system: WGS84 (EPSG:4326)
- Used for: district population aggregation (zonal statistics), population
  heatmap, grid-level AHP analysis

4.4 Road Network
- Source: OpenStreetMap (OSM) via OSMnx Python library
- Network type: drivable roads ("drive" network type)
- Extent: entire Lebanon bounding box
- Cached as: road_graph_lebanon.graphml (avoids re-downloading)
- Graph size: approximately 100K nodes, 150K edges
- Edge attributes: length (meters), highway type, maxspeed tags
- Travel time computed per edge using speed assumptions based on highway type

4.5 Regulatory and Standards Data
- Encoded programmatically in lebanon_ems_rules.py
- Sources: LRC/IFRC INP 2023, MoPH Karar 473/2021, EU EMS standards, WHO
- Not sourced from a database but from published documents and standards

CHAPTER 5: METHODOLOGY (AHP FRAMEWORK)
================================================================================

5.1 Overview
- The AHP model evaluates each of Lebanon's 26 districts on three criteria
  to produce a composite priority score indicating need for new EMS coverage.

5.2 Decision Hierarchy

  Goal: Prioritize districts for new EMS station placement
  |
  |-- Criterion 1: Travel-Time Gap (Accessibility)     Weight: 50%
  |-- Criterion 2: Population Density (Demand)          Weight: 30%
  |-- Criterion 3: Exposed Population (Equity)          Weight: 20%
  |
  Alternatives: 26 districts of Lebanon

5.3 Criterion Definitions

  Criterion 1 - Travel-Time Gap (C1) [Weight: 50%]
  - Measures: minimum road travel time (in minutes) from the district centroid
    to the nearest EMS station
  - Computed via: multi-source Dijkstra shortest path on the OSM road graph
  - Interpretation: higher travel time = worse accessibility = higher priority
  - This is the most heavily weighted criterion because response time is the
    primary determinant of EMS effectiveness

  Criterion 2 - Population Density (C2) [Weight: 30%]
  - Measures: people per square kilometer in the district
  - Computed as: total population (from WorldPop zonal sum) / district area (km2)
  - Interpretation: denser districts have more potential patients per unit area,
    so they benefit more from a nearby station

  Criterion 3 - Exposed Population (C3) [Weight: 20%]
  - Measures: total population in districts where the nearest EMS station is
    beyond the coverage threshold (default: 10 minutes by road)
  - If a district IS covered (nearest station <= threshold), exposed pop = 0
  - Interpretation: captures the absolute number of people at risk, not just
    density or travel time

5.4 Normalization
- All three raw criterion values are min-max normalized to [0, 1]:
  norm_value = (value - min) / (max - min)
- This puts all criteria on the same scale before weighting
- Normalization is computed across all 26 districts

5.5 Score Formula
  AHP_Score = 0.50 * norm_access_gap
            + 0.30 * norm_pop_density
            + 0.20 * norm_exposed_pop

  Result: a score between 0.0 and 1.0 for each district
  Higher score = higher priority for new EMS coverage

5.6 Priority Classification
- Districts are ranked by AHP score and classified using quantile thresholds:
  - HIGH priority:   top 20% of scores (approximately 5-6 districts)
  - MEDIUM priority: top 21-50% of scores (approximately 7-8 districts)
  - LOW priority:    bottom 50% of scores (approximately 13 districts)
- Quantile-based classification avoids fixed thresholds that could cluster
  all districts into a single category

5.7 Why These Weights?
- Travel-time gap (50%): response time is the single most critical factor in
  EMS effectiveness; every minute of delay reduces survival probability
- Population density (30%): reflects demand concentration; a station in a dense
  area serves more people per unit investment
- Exposed population (20%): equity consideration; ensures large populations
  beyond coverage threshold are not ignored even if density is moderate

5.8 Live Model Adjustability
- The dashboard allows users to adjust all weights via sliders in real time
- Weights auto-normalize to 100% when any slider changes
- Coverage threshold is also adjustable (default 10 min)
- Priority thresholds (percentiles) can be changed
- All scores, rankings, and map colors update instantly

6.5 Data Processing Pipeline (phase1_ahp_explore.py - 1,538 lines)

  Step 1: Load district boundaries from GADM GeoJSON
  Step 2: Load EMS station locations from Excel
  Step 3: Load population raster (WorldPop GeoTIFF)
  Step 4: Spatial join - assign stations to districts
  Step 5a: Zonal statistics - aggregate population per district from raster
  Step 5b: Dissolve duplicate GADM districts (merge by NAME_2)
  Step 5c: Download/load OSM road graph (cached as GraphML)
  Step 5d: Compute travel times on road edges based on highway type and speed
  Step 5e: Multi-source Dijkstra - find min travel time per district to
           nearest station; compute AHP scores and classify priorities
  Step 5f: Create 1 km grid from population raster
  Step 5g: Compute grid-level travel times
  Step 5h: Grid-level AHP scoring with density boost (1.2x for cells >= 2000
           pop/km2) and 30-min travel time cap
  Step 5i: Apply the station-proposal rule - select grid cells that are
           high-density (>= 2000 residents/km2) AND not reachable by any
           existing station within 10 minutes; DBSCAN-cluster these qualifying
           cells (one proposed station per cluster). The rule alone decides
           WHERE stations are proposed; AHP scores only rank them.
  Step 6:  Generate interactive Folium map with all layers
  Step 7:  Build dashboard panel HTML (KPIs, tables, filters, Copilot UI)
  Step 8:  Inject everything into HTML template and write final dashboard
  Step 9:  Write AHP sidecar JSON for Copilot consumption

6.6 Travel Time Computation Details
- Each road edge in the OSM graph gets a travel_time attribute
- Speed is determined by: maxspeed tag if available, else default by highway type
  - motorway: 100 km/h
  - trunk: 80 km/h
  - primary: 60 km/h
  - secondary: 40 km/h
  - tertiary: 30 km/h
  - residential: 20 km/h
  - other: 20 km/h
- travel_time (seconds) = edge_length (meters) / (speed km/h * 1000/3600)
- Multi-source Dijkstra starts from all EMS station nodes simultaneously
- For each district centroid, finds the shortest travel time to any station

6.7 Grid-Level Analysis
- Population raster cells (1 km) are converted to point geometries
- Each grid cell gets its own travel time and AHP score
- Density boost factor: cells with >= 2000 pop/km2 get 1.2x multiplier
- Travel time capped at 30 minutes for normalization stability
- Grid cells enable finer spatial resolution than district-level analysis

6.8 Candidate Station Identification (Rule-Based + DBSCAN Clustering)
- Governing rule (the official placement criterion): a new station is proposed
  wherever a HIGH-DENSITY area cannot be reached by an existing station in time:
    1. population density >= 2000 residents/km2, AND
    2. NOT reachable by any existing EMS station within 10 minutes
       (realistic road-network travel time, the covered_10min flag)
  Both conditions must hold. Density alone is not enough (a dense but already
  covered area is not proposed), and a reachable area never receives a proposal.
- This rule is WEIGHT-INDEPENDENT: the AHP weights do not decide where stations
  are proposed. They only RANK the resulting proposals. Consequently the set of
  proposed locations is identical across all weight presets; only the ranking
  and priority tiering change.
- Step 1 - Gate: select the 1 km grid cells satisfying both rule conditions.
- Step 2 - Cluster: DBSCAN (Density-Based Spatial Clustering) groups the
  qualifying cells into service areas, one proposed station per cluster.
  - eps = 3 km (cells within ~3 km join the same station)
  - min_samples = 1 (every qualifying cluster yields a station)
- Step 3 - Place & summarize, per cluster:
  - Location = population-weighted centroid of the qualifying cells
  - Population served = total population within the station's coverage radius
  - Uncovered population = population of the qualifying (dense + unreachable) cells
  - Mean AHP score of the cluster cells (under the active weight preset)
  - Coverage radius derived from the cluster's spatial spread (1.5-6 km)
- Ranking: proposals are sorted by AHP mean score (uncovered population as a
  tiebreak). Priority tiers (High/Medium/Low) are assigned by score quantiles.
- Result (default "Balanced" preset): 32 proposed stations, every one of which
  has uncovered population > 0 and a mean travel time greater than 10 minutes -
  i.e., each proposal addresses a genuine, currently-unreachable coverage gap.

7.4 Key Design Decisions
- Single HTML file: no web server needed to view the dashboard (just open in
  browser). Makes it portable and easy to share.
- Monochrome UI theme: black-and-white panel design so the only color is on
  the map, making priority colors (red/orange/green) unambiguous.
- Local-only processing: all data stays on the user's machine. No cloud APIs,
  no data uploads, no API keys required.
- Deterministic + optional LLM: Copilot works without AI model installed;
  Ollama enhances but is not required.

CHAPTER 9: AI-POWERED EMS COPILOT
================================================================================

9.1 Overview
- An AI chat assistant embedded in the dashboard
- Answers questions about EMS coverage, district data, AHP methodology,
  and station placement
- Runs 100% locally via FastAPI backend + optional Ollama LLM
- No API keys, no internet calls for AI inference

9.2 Architecture
- Frontend: chat panel in dashboard (floating button, message history,
  input field, suggestion chips)
- Backend: FastAPI server (copilot_server.py) on http://127.0.0.1:8000
- Endpoints:
  - GET /health: checks server status, Ollama availability, AHP data loaded
  - POST /chat: accepts {message, use_llm}, returns {answer, intent, data}
- CORS enabled for cross-origin browser requests

9.3 Intent Routing
- Regex-based intent classification (no ML needed for routing):
  - PLACEMENT: "where can I open an EMS center in [location]?"
  - COMPARISON: "compare [district A] and [district B]"
  - PRIORITY/RANKING: "which districts are highest priority?"
  - DISTRICT LOOKUP: "tell me about [district]" or "how many stations in [X]?"
  - AHP EXPLANATION: "what is the AHP model?" or "how does scoring work?"
  - GOVERNORATE SUMMARY: "summarize [governorate]"
  - NATIONAL SUMMARY: "give me a national overview"

9.4 Deterministic Data Tools (always available, no LLM required)
  - tool_district_info(name): returns population, stations, AHP score/priority,
    travel time for a specific district
  - tool_compare(a, b): side-by-side comparison of two districts
  - tool_top_priority(n): returns top-N districts ranked by AHP score
  - tool_governorate_summary(name): aggregates all districts in a governorate
  - tool_national_summary(): nationwide KPIs and statistics

9.5 Spatial Placement Assessment Tool
- When user asks "where should I place a station near [location]":
  1. Geocodes the location via OSM Nominatim API (or parses coordinates)
  2. Determines urban/rural classification by governorate
  3. Applies spacing heuristics: 1.5 km minimum (urban), 5 km (rural)
  4. Checks for overcrowding (>= 2 existing stations within min spacing)
  5. Returns verdict: adequate / tight / overcrowded
  6. Suggests underserved district alternatives if placement is poor

9.6 LLM Integration (Optional)
- Model: Ollama running qwen2.5:3b locally (~3GB disk, ~6GB RAM)
- System prompt enforces:
  - Never invent numbers; use only TOOL_RESULT data
  - Reference Lebanese standards with citation keys ([LRC-9], [MoPH-473], etc.)
  - Keep answers under 200 words
  - No emojis
- If Ollama not installed: deterministic templated responses (still fully
  functional, just less conversational)

9.7 Status Indicator
- Green dot: Copilot backend online and responsive
- Red dot: backend not running or unreachable
- Status checked every 3 seconds via /health endpoint polling

CHAPTER 11: CANDIDATE STATION RECOMMENDATIONS
================================================================================

11.1 Methodology
- Proposed stations follow the official placement rule (see Section 6.8): a
  station is proposed wherever a high-density area (>= 2000 residents/km2)
  cannot be reached by an existing station within 10 minutes by road.
- Qualifying 1 km grid cells are clustered with DBSCAN (eps = 3 km,
  min_samples = 1); each cluster yields one proposed station placed at the
  population-weighted centroid.
- The rule alone decides WHERE stations are proposed (it is weight-independent);
  AHP weights only RANK the proposals and assign their High/Medium/Low tier.
- Default run ("Balanced" preset): 32 proposed stations. Each one has uncovered
  population > 0 and a mean travel time > 10 minutes, so every proposal
  addresses a genuine coverage gap (no proposals in already-covered areas).
- Each candidate includes: coordinates, population served, uncovered
  population, mean travel time, coverage radius, and a spacing assessment.

11.2 Spacing Assessment Logic
- For each candidate location:
  - Count existing stations within minimum spacing distance
    (1.5 km urban, 5 km rural)
  - If 0 nearby stations: "Adequate" spacing
  - If 1 nearby station: "Tight" spacing
  - If >= 2 nearby stations: "Overcrowded" (not recommended)

CHAPTER 12: LIMITATIONS & FUTURE WORK
================================================================================

12.1 Current Limitations
- Lebanon does not publicly codify a spatial spacing rule for EMS bases.
  The 1.5 km / 5 km thresholds used are transparent demo heuristics derived
  from the 9-minute response target, not legal requirements.
- Travel time uses the OSM static road graph; real-time traffic, road
  closures, and seasonal conditions are not modeled.
- The EMS station list is an operational snapshot and may not reflect every
  currently active or recently opened/closed facility.
- Population data is from WorldPop 2025 estimates; actual population may
  vary due to displacement, seasonal migration, and refugee populations.
- AHP weights (50/30/20) are project defaults; different stakeholders may
  have different priorities (the dashboard allows live adjustment).
- The model uses district centroids for travel time calculation; within large
  districts, actual travel times vary significantly by location.
- Grid-level analysis partially addresses this but is computationally heavier.

12.2 Future Work
- Incorporate real-time traffic data for dynamic travel time estimation
- Add demand-side data (historical call volumes, incident locations)
- Include terrain/elevation as an additional criterion
- Pairwise comparison matrix for formal AHP consistency checking
- Multi-scenario analysis (disaster response, conflict zones)
- Integration with hospital/healthcare facility locations
- Mobile-responsive dashboard design
- Add more LLM models for enhanced Copilot capabilities
- Extend to other countries or administrative levels

CHAPTER 13: CONCLUSION
================================================================================

- This project successfully developed a comprehensive, data-driven decision
  support system for EMS station placement in Lebanon using the AHP methodology.
- The system integrates four open data sources (GADM, WorldPop, OSM, EMS
  station records) into a unified analytical pipeline.
- Three weighted criteria (travel-time gap, population density, exposed
  population) produce transparent, auditable priority scores for all 26
  Lebanese districts.
- The interactive dashboard allows stakeholders to adjust model parameters
  in real time and immediately see the impact on priorities and map
  visualization.
- The AI-powered EMS Copilot provides accessible data querying without
  requiring GIS expertise.
- Key finding: Minieh-Danieh, Akkar, Jubail, Baalbeck, Chouf, and Beirut are
  the highest priority districts for additional EMS coverage under the default
  AHP model, driven primarily by the travel-time gap (large under-served areas
  far from any existing station) rather than density alone.
- New EMS stations are then proposed by a transparent rule - a high-density
  area (>= 2000 residents/km2) that cannot be reached within 10 minutes -
  yielding 32 concrete, justifiable candidate locations.
- The system runs entirely locally, ensuring data privacy and eliminating
  dependency on cloud services.
